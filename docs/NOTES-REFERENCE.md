**Distant geometry not being drawn (solved, cxldsakeb, 2026-10-16):** with the native VU1 and the game already running smoothly, cxldsakeb sees that only nearby things are drawn: what lies ahead of Kratos appears **little by little with distance**, and where it's missing you see **the sky or the background**. In the first area the ceiling, the arches and the lower part of the walls are missing, and NPCs get hidden too (on the PS2 the room is closed and you see the Colossus through the large windows). **Cause located, no fix yet:**
- Order of each frame (local per-batch log): clear (color + Z = 0) → **sky, sea and background, writing Z** (`GEQUAL`, Z `0x80EAC4`–`0x81D95A`: `tbp` `35C0`, `3600`, `3540`, `34C0`, `2CC0` with alpha test `GEQUAL 0x60` + `AFAIL RGB_ONLY`, and two draws **with no texture and no alpha test**, the sea, in the horizontal strip) → **room** (`GEQUAL`, Z mostly `0x800A49`–`0x80CD7C`) → fog (`GREATER` at fixed Z `0x80FFFF`, blending by destination alpha) → bloom → Z-only clear → HUD (`ALWAYS`, Z `0x7FF98E`).
- The room has **lower Z than the sky and the sea**, so it fails the test and disappears. With `GOW_GS_HW_NODEPTH=1` everything shows; without Z writes in the sky textures, the ceiling and windows appear (the sea strip stays covered).
- Since the sea writes Z without an alpha test on the PS2 too, there **the room must have higher Z** than ours: the Z values reaching the GS are not the PS2's. It's not the VU1 (the interpreted one gives the same), nor the frontend (reading of `XYZ2`/`XYZF2` and of `ZBUF_1`/`_2` reviewed against PCSX2), nor the EE (comparator against PCSX2's interpreter over the 6,607 function starts: only 1-bit roundings and VU0 flags that are never read). **Remaining suspect: the VIF1** (`UNPACK` with row/mask modes, which carries vertices and constants into VU1 memory; it's the runtime's own code). Next: compare the Z values of the same scene in PCSX2 (GS dump) and go over `ps2_vif1_interpreter.cpp` against PCSX2.
- Also ruled out: clamping Z to 24 bits like PCSX2 (normalize by 2³² and clamp on write): it changes nothing here (the room uses `XYZF2`, 24-bit Z by definition) and doubles `gs_ms` because of writing `gl_FragDepth`. The patch stays local.
- EE comparator: `PS2X_EE_DIFF=all` doesn't work in GoW II (it wraps the resume points and the dispatcher gets lost: `No exact recompiled function`). With a list of function starts it does work (local change in `ee_diff.cpp`, `PS2X_EE_DIFF=@file`, one address per line, taken from `config/funcmap.csv`).
- Along the way: the recompiler translates `movn`/`movz` as a 128-bit copy (`SET_GPR_VEC`); on the R5900 they only write the low 64 bits (seen at `0x29AD98`). **Fixed** (cxldsakeb, 2026-10-17, fork): `ps2_recomp` now translates them with `SET_GPR_U64` (like the PCSX2 interpreter that the runtime carries, `ee_ref`: only `UD[0]`); in GoW II that's 1,835 instructions in 827 functions.

Ruled out earlier:
- **GS fog (`FGE`)**: the hardware backend doesn't implement it, but **GoW II doesn't use it** (`GOW_GS_INVENTORY=1`: `fog=0` in ~2 million draws per interval; `PS2X_GS_FOG_FORCE=FF00FF` tints nothing). An implementation following the GS manual stays local, not committed, because nothing exercises it.
- **The native VU1 discarding polygons**: `GOW_VU1N_VERIFY=200000` compares each native run with the exact VU1 and **there is no difference at all in the ADC bit** (the "don't draw this vertex" one). There is ~1 % of runs with small differences, to be reviewed separately: 1-bit rounding on huge values (`…192`/`…193`), MAC *flags* at the end (`68`/`8e8`) and a `0x400`/`0` word in the packets.

**Upscaling fixes (DaniSBR1, 2026-10-19): the ghost, the bright right edge and the blue line.** Three bugs that only showed at internal scale > 1, all in how `gs_hw_backend.cpp` reads a render target drawn at scale k as a texture (details in "Blockers", 19–21). **Checked by DaniSBR1 playing for ~30 min:** the ghost and the blue line are gone, and the right edge is clean.
- **The game's post-processing chain** (local per-draw log, every pass samples a render target): 1:1 copy of the frame to `fbp=232` at texel centres (`u = x + 0.5`, linear); two halvings (`x → u = 2x + 1`) into `120`/`152`; blur passes that keep 64, 128 and 256 px wide images side by side in `120` (a 640 px wide target) and read them with `CLAMP = 5`; an enlargement (`u = x / 2`); the bloom added to the frame with `ALPHA = 0x59…68` (`Cs·Ad + Cd`). Separately, the shadows copy a byte of the Z buffer into the frame (the Z16 copy of blocker 13) and a `T8H` pass remaps the frame's alpha through a CLUT: **a depth haze**, which the game adds with the destination alpha.
- **Method that worked:** compare at `PS2X_GS_HW_SCALE=1` (the GS exactly, no upscaling) against 2; remove passes with `GOW_GS_HW_SKIPTBP` (with `1300` there is no bloom and the right-edge band disappears); a local log of the draws that sample a render target (positions, `u/v`, filter, `CLAMP`, alpha; not pushed); and, for things that need a human eye, a local F9 key that toggles the fix under test while playing.

**Real speed (cxldsakeb, 2026-10-17):** the F10 counter is no use (it always shows 60). The good measurement is `GOW_PERF_DIAG=1` with **`GOW_PERF_FRAME_PC=0x14E380`** (the function that sends each frame to the GS, once per game frame), which gives `guest_flip_hz`. On cxldsakeb's PC, with native VU1 and IOP: **60 on the title screen and menu, ~44–59 in the first area with combat**. There the EE already waits ~35 % of the time (`guest_wait_ms` ~1,700–1,900 out of 5,000): what dominates is the GS thread (`gs_ms` ~3,000–3,500) and the VU1 (~2,700). During movies, `[0x2D8108]` counts VBlanks without resetting to 0 (`GOW2_PEEK=2D8108` with `GOW2_THREAD_WATCH=5`): 300 every 5 s = real time.

**Since fork `19c65a5` F10 shows the real FPS** (`FPS: … [G]`): the override tells the runtime to count the entries into `0x14E380` (`ps2_perf::setGameFramePc`). In combat it shows ~50 with VPS 60 and speed 100 %: emulated time runs at real time and the game draws ~50 frames per second.

**What limits the ~48–50 FPS in combat (cxldsakeb, 2026-10-17):** `0x14E380` sends the frame (`0x14D150`) and **immediately waits for its FINISH** (`0x18ADD0`, busy wait) before going back to prepare the next one; with `GOW2_THREAD_WATCH`, thread 1 almost always shows up at `pc=0x18ADEC`. So each frame costs, in series, the time the EE takes to prepare it (~12 ms) plus the time the VIF1 *worker* takes to run the VU1 (~12 ms; `vu_ms` ~2,850 out of every 5,000 in all tests) and for the GS to finish. On the PS2 it's the same, just faster. To reach 60, the EE code or the VU1 code has to be sped up by ~25 %. Tried and ruled out:
- **Building in `Release`** (`/Ob2`) instead of `RelWithDebInfo` (`/Ob1`): lowers `ee_ms` (~3,000 → ~2,550) and `gs_ms`, but the FPS don't change (~47–48): the EE just waits longer. Not worth it (19 min of extra build time).
- **Bigger GS thread queue** (`PS2X_GS_QUEUE_CHUNKS=256`, default 8 blocks of 64 KB): same FPS.
- Runtime threads, in case they're needed: `GameThread` (EE), the VIF1/GIF *worker* that runs the VU1 (`PS2X_GS_WORKER=1`), the GS frontend stage (`gs_stage.cpp`) and `GSThread` (OpenGL).
- Ideas for later: every `jal` in the generated code goes through `dispatchGuestBranch` (one runtime call per game call); calling the recompiled function directly when the target is fixed would trim some EE time, but `dispatchGuestBranch` is already light (trace ring, *checkpoint* and table lookup): a rough estimate, ~10 %, not the ~25 % that's missing. Not measured; it's a recompiler change, to be discussed first. The other half, the native VU1, is the other route.

## Sony library stubs

The 79 from the GoW1 template, searched for in GoW II: **76 located** (in `config/recomp.template.toml`) and **3 that aren't linked** in GoW II. DaniSBR1, 2026-10-15.

**Method.** Sony's libraries are in the same order and almost the same layout as in GoW1, just shifted as a block. For each stub, its library's offset is applied to the GoW1 address (that only gives the hypothesis, rule 2) and it's checked in the GoW II ELF that a function starts there, that the size matches the one in `referencia/gow1/config/funcmap.csv` (±4 bytes: a padding `nop` that each tool counts in a different function) and, if it doesn't match, that the end also falls in place (that is, that Ghidra split the function differently). When possible, it was confirmed by an independent route: strings the function uses, what it calls, or the code itself.

| Group | Offset | Stubs | Independent checks |
|---|---|---|---|
| libmpeg | +0x3C0E8 | `sceMpegCreate`…`sceMpegAddStrCallback` (10), `0x2AB3E0`–`0x2B01D8` | 6 match in size; the other 4 match at both ends |
| libipu, libgraph, libdma, libcdvd | +0x3C0F0 | `sceIpu*` (4), `sceGs*` (4), `memclr`, `sceDma*` (5), `sceCd*` (4), `0x2B53D8`–`0x2B6CC0` | `sceGsSyncPath` (`0x2B5BC8`) prints `"sceGsSyncPath: …"`; `sceCdInit` (`0x2B6900`) uses `"Libcdvd bind err %d CD_Init %d"` and `"Libcdvd Exit"` |

**SDK 3.0: C functions in front of the syscalls.** `StartThread`, `iWakeupThread` and `InitTLB` are libkernel C functions that end up calling the syscall wrapper (`0x2CF740`, `0x2CF860`, `0x2CFD90`, which only they call). In GoW1, `iWakeupThread` and `InitTLB` seemed to land "in the middle of a function" because its map merged two functions into one (`InitThread`+`iWakeupThread`: `0x2D0510 + 0xF0 = 0x2D0600`).

**Not linked in GoW II** (left out):
- `exit`: nobody calls `_exit` (`0x1001D0`, the boot one) except `abort` (`0x2C7820`, which does `_exit(1)`), nor `Exit` (`0x2D5218` → syscall 4 at `0x2CF540`) except the boot code and libkernel. A PS2 game never exits.
- `read` and `sceTtyRead`: in the libkernel area the sequence of sizes jumps from `write` to the next function, and from `sceTtyWrite` straight to `sceTtyInit`.

**Stubs by name (to watch in phase 2).** Besides the ones in the template, `ps2_recomp` turns into stubs the syscall wrappers that Ghidra gives a library name to (`sceSifSetDma`, `sceSifDmaStat`, `sceSifSetDChain`, `sceSifSetReg`, `sceSifGetReg`, `sceSifStopDma`, `isceSifSetDma`, `isceSifSetDChain`): with the 76 from the template that makes 84 stubs. Measurements on DaniSBR1's PC (Ryzen 5 5500, 6 cores / 12 threads, 16 GB, repo on HDD), recompiling the whole runner (deleting its `.obj` files), with a script that samples every 5 s the number of concurrent `cl.exe`, the CPU and the RAM, plus the MSBuild summary (`/clp:PerformanceSummary`).

| | Before | With `/MP6` |
|---|---|---|
| **Total time** | **40 min 24 s** | **21 min 13 s** (1.9× faster) |
| Compile (`ClCompile`) | 2,389 s (98.6 %) | 1,243 s |
| Link (`Link`) | 30 s | 26 s |

- **Cause:** the Visual Studio generator compiles a project's files one at a time unless it is given `/MP`. `--parallel` only runs different projects at the same time. The runner's 207 blocks were compiled serially.
- **`/MP`** (fork, `ps2xRuntime/CMakeLists.txt`): for `ps2EntryRunner` and `ps2_runtime`. The number of compilers is derived from each PC's RAM and cores (1.5 GB per compiler and 6 GB for the system: 6 on 16 GB / 12 threads, about 17 on 32 GB / 32 threads, 1 = no parallelism below ~8 GB). It is changed with `-DPS2X_MSVC_MP_PROCESSES=N`. CMake shows it when configuring: `PS2X: MSVC parallel compilation /MP6`. Turning it on does not make MSBuild recompile anything.
- **Content-based copying** (`scripts/recompile.ps1`): it copies to the runner only the files whose content changed (size and, if that matches, MD5), without touching the timestamps of the rest, and only deletes copies that no longer exist. Before, it deleted everything and copied it all with the current timestamp, and every sync recompiled the whole runner.
  - `-SyncOnly` with no changes: **0 files copied and 0 blocks recompiled** (the build, 6 s). Before: full recompile.
  - Changing an override and `-SyncOnly`: **1 file copied, 1 block recompiled, 21 s**.
  - The comparison reads every file: 40–170 s on HDD depending on the Windows cache.
- **Verified:** the game reaches the playable area just as before (FPS 57.99 `[B]`, VPS 60, speed 100 %, no `missing-target`).
- **Not much help here:** moving the build to an SSD (linking is 30 s out of 40 min). Optional on each PC: exclude the repo folder from Windows Defender, which during the build scans thousands of new files and takes ~400 MB.
- A change to a header that includes everything (`gs_frontend.h`, `ps2_recompiled_functions.h`…) still forces a full recompile, but now in half the time.
- **cxldsakeb's PC** (Ryzen 9 5900XT, 16 cores / 32 threads, 32 GB, repo on HDD): full runner recompile after the `gs_frontend.h` change, **12 min 53 s** (before ~38 min), with no `LNK2001`/`LNK2019`.

## Launcher (DaniSBR1, 2026-10-20)

## Memory card: performance (fixed in the fork, cxldsakeb, 2026-10-17)

`MemoryCard::persist` (`ps2xIOP/src/emulator/core/memory_card.cpp`) **opens, writes and closes the 8 MB file on every page** (528 bytes) that is written or erased; the first write dumps the whole image. Formatting and saving are thousands of pages, and with the repo on a mechanical hard drive it is very noticeable. Proposed fix: keep the file open (or write to memory and flush at the end of each operation or on close). First measure how long a full format takes once blocker 16 is confirmed.

## Diagnosing blockers (overrides/gow2_overrides.cpp)

They only activate with the environment variable; without it they change nothing.

- `GOW2_THREAD_WATCH=<s>`: every `<s>` seconds, the EE threads (`status`, wait, `pc`, `ra`). For silent blockers: if a `status=0` thread repeats the same `pc` while the cycle count advances, it is a busy loop. Like `GOW_THREAD_WATCH` in GoW1.
- `GOW2_BOOT_TRACE=1`: counts calls to the functions in the boot sequence (`sceSifRebootIop`, `sceCdInit`, `sceSifInitRpc`…) and logs each `sceSifLoadModule` (path and result) and each `sceSifBindRpc` (server and result).
- From the runtime, without recompiling: `PS2X_TRACE_RPC=<prefix>` logs the RPC calls that reach the IOP (e.g. `8` for Sony's servers).
- From the runtime, for the IOP: `PS2X_IOP_TRACE=<n>` logs the first `n` import calls (`[IOP:trace] #k libreria:ordinal a0=… ra=…`); `PS2X_IOP_TRACE_NOCLIB=1` drops `sysclib` (most of the volume) and `PS2X_IOP_TRACE_EVERY=<n>` samples one in every `n`. With `PS2X_TRACE_RPC=123` you see the EE's RPCs to SMPD (`sid 0x123456`/`0x123457`) with their first 8 words. That is how blockers 6 to 8 were found.
- `GOW2_CALL_PROFILE=<s>` (override): wraps every game function and, every `<s>` seconds, prints the 25 most called. **It is the best tool for a silent loop:** the loop's functions come out on top, and if only one address shows up, the loop calls nothing (blocker 8). It takes a few more seconds to boot.
- `GOW2_PAD_SCRIPT` (override): controller presses at fixed times (seconds since the first controller read), to repeat a sequence without a keyboard. `"T:boton"`, `"T1-T2/P:boton"` (every `P` seconds) or `"T1-T2:boton"` (held for the whole interval). Buttons: `start`, `select`, `x`, `o`, `sq`, `tri`, arrows (`up`…), `l1`, `r1`, `l2`, `r2`, and the left stick at full tilt: `lup`, `ldown`, `lleft`, `lright` (e.g. `125-165:lup`, walk for 40 s). E.g.: `GOW2_PAD_SCRIPT=15:start,20-60/3:x` (title screen → menu → new game). In the log: `[gow2-pad2:script]`.
- `GOW2_MOVIE_TRACE=1` (override): wraps the video player's functions (`0x191AB0` next frame, `0x191BD0` finished?, `0x18FE08` is there audio?, `0x25EF40`, `sceMpegIsEnd`) and prints every change in result with the player state (`[0x2D8190]`), whether it can be skipped (`[0x2D8194]`) and the movie's counters (`[0x337700]` → `+0x54` frames shown, `+0x140` mode, `+0x154` end). It also prints the first deliveries to the audio callback (`[gow2-movie-audio]`: length, first bytes, ring), what is uploaded to the SPU2 (`[gow2-movie-spu]`: the flags of each ADPCM block) and the voice position (`spuPos5b`, 989snd's `0x5B` command). With `GOW_MPEG_DIAG=1` (runtime) you also see the stream callbacks (`[MPEG:diag] stream callback`) and the pacing (`[MPEG:sync]`). That is how blockers 17 and 18 were found.
- `GOW2_PEEK=dir,dir,…` (override, with `GOW2_THREAD_WATCH`): prints those EE memory words on each pass. For following game variables (loader state, flags).
- `PS2X_IOP_TRACE_DMA=1` (runtime): every IOP-to-EE DMA, with source, destination, size and the first 16 bytes.
- `GOW_GS_HW_STATS=1` (runtime): GS draws, batches and textures per interval. Useful for knowing whether the game is drawing without looking at the screen.
- **The `pc` from `GOW2_THREAD_WATCH` does not always indicate a hang:** in recompiled code it is only updated at certain points (when returning from a call, for example). A main loop that spins every frame also always shows the same `pc`. To know whether it is progressing, look at the activity (RPC, IOP imports).
- `tools/elf_dis.py` needs `capstone` from the user's environment: run it with plain `py -3` (with `py -3 -I` it does not find it).
- To test an override without recompiling everything: copy only `overrides/gow2_overrides.cpp` to `PS2Recomp/ps2xRuntime/src/runner/`, `touch` it and `cmake --build` (~1 min; only its unity build block changes). `recompile.ps1 -SyncOnly` re-timestamps the 6,600 files and recompiles everything (~50 min). Run CMake from Bash: in PowerShell, with `_common.ps1` loaded, the first warning on stderr aborts the command.

## Resource loader and SMPD protocol

cxldsakeb, 2026-10-16 (blockers 7 to 9). Taken from `PS2X_TRACE_RPC=123`, `PS2X_IOP_TRACE_DMA=1` and the disassembly.

- **RPCs to SMPD's `0x123456` server, all in mode 1 (no wait).** They are sent with `0x2A7FA0`: it waits for the previous one to finish (`sceSifCheckStatRpc`), calls `sceSifCallRpc` and waits for the reply with `0x2A7C10`. Commands seen:
  - `fn 0x68` with nothing else: **registration**. The EE gives SMPD two of its buffers, `0x338500` (0x40 bytes, receives the TOC date) and **`0x338540` (0x5C0, status block)**. SMPD writes there by DMA a sequence number (`+0`) every time something changes, and the request **slots** (`0x338540 + 0xF4 + index*0x24`).
  - `fn 0x68` with a name: **request for a resource** (`R_LglScA`, `R_PermA`, `SBP_general`…; type `0xF` = WAD, `0xD` = sound bank).
  - `fn 0x4C`: **"give me data"**. SMPD sends it by DMA to the EE's double buffer (`0x3DD2C0` / `0x3FD2C0`, chunks of up to 0x20000 bytes).
  - `fn 0x4D`: a **packet** with several commands inside (`n`, then `size<<16 | fn` for each).
- **The loader `0x18CF70`** is a state machine (`[0x2D8130]`). It reads 0x20-byte headers from the input buffer (`[0x2D8168]`, bytes available at `+0x10`) and processes the chunks. **It works until it exhausts a per-frame time budget**, measured with the `Count` register (hence blocker 8), and returns 1 while it still has work. If `[0x2D8154] ≠ 0` (**paused**), it returns 1 immediately.
- **Pause and resume:** `0x17ED58` (counter `[0x2D8154]`++) and `0x17ED98` (−−).
- **Pending requests:** walked by `0x17F170`, called from `0x17F578` together with the SMPD poll (`0x2A7990`). State at `+0x38`: **2** = waits for the slot to have bit `0x2000` at `+0x20` (if `+0` ≠ 0 it moves to 3; if 0, not found: resumes and moves to 5); **3** = sends read subrequests (`0x2A8A88`, command 0x13, up to 8 per pass) and when done resumes (4).
- **Load wait:** `0x1EAAE0` (inside `0x1EA8D8`), `do { 0x17F578(); 0x25F140(); } while (0x18CF70())`.
- **Sound banks:** SMPD fetches the bank from the EE (`sceSifGetOtherData`, 0x2000-byte chunks), hands it to 989snd (`snd989:129`) and that uploads it to the SPU2 with `sceSdVoiceTrans`. Without the native LIBSD replacements, that waits for an SPU2 DMA that does not exist (blocker 9).
